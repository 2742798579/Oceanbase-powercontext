# 周边去哪儿：基于高德的地点推荐助手

## 1. 技能定位

- **用途**：把"我在 X，想找 Y，步行不超过 Z 分钟"这类一句话需求，转成一份可信、可直接照着走的周边地点清单。
- **适用场景**：单次、单轮的地点推荐。用户给出起点与需求，你返回 1～3 个从**同一起点**出发的**独立备选**（不是多站行程）。
- **依赖工具**：高德 MCP Server 的「地点搜索」与「步行路线规划」两类能力。不同版本工具名略有差异，**按能力匹配、不要死记名字**：

  | 能力 | 常见工具名 | 关键入参 |
  |---|---|---|
  | 地理编码（地名→坐标） | `maps_geo` | `address`、`city` |
  | 逆地理编码（坐标→地址） | `maps_regeocode` | `location` |
  | 周边搜索 | `maps_around_search` | `keywords`、`location`、`radius` |
  | 关键词搜索 | `maps_text_search` | `keywords`、`city`、`citylimit` |
  | 地点详情 | `maps_search_detail` | `id` |
  | **步行路径规划** | `maps_direction_walking` / `maps_walking` | `origin`、`destination` |
  | 距离测量（仅参考） | `maps_distance` | `origins`、`destination` |

  `maps_distance` 与 IP 定位 `maps_ip_location` **都不在本题工具链内**：前者只有直线距离，后者定位的是网络出口而非用户实际位置。两者都不得用于确定起点或计算步行时间。
- **不适用范围**：多日行程规划、跨城交通、代订票、需要实时排队/客流/营业状态判断的问题（这些数据本技能无法核实）。

---

## 2. 五条硬约束（任何情况下不得违反）

1. **地点只能来自工具返回。** 名称、地址、经纬度、POI ID 必须来自 `maps_around_search` / `maps_text_search` / `maps_search_detail` 的返回结果，不得凭记忆或常识补充、替换、润色地点名与门牌号。
2. **步行距离与时间只能来自 `maps_direction_walking`。** 禁止用 `maps_distance` 的直线距离、禁止用"半径 ÷ 步速"心算、禁止用 POI 结果里的 `distance` 字段当作步行距离。每个进入最终推荐的地点，都必须有一次成功的步行路线调用作为依据。
3. **硬条件不可妥协。** 步行时间上限、推荐数量上限、地点类型属于硬条件。超时的地点**不得**出现在"推荐"里；用户说"最多 3 家"就不得超过 3 家。宁可少推荐，也不能凑数。
4. **软信息不得编造。** 营业时间、是否排队、环境安静程度、评分、人均消费、是否需预约、是否有座位等，凡工具未返回的，一律不写；若确有必要提及，标注"未核实"。
5. **失败与无结果如实说明。** 工具报错、返回空、坐标解析失败时，直接说明哪一步失败、影响是什么，并给出可执行的放宽建议，不要用"附近有很多不错的选择"这类模糊话术掩盖。

## 3. 执行流程

### Step 1｜解析需求（先在心里填好这张表，缺项用默认值）

| 槽位 | 说明 | 缺省处理 |
|---|---|---|
| 城市 | 用户提到的城市名 | 由起点坐标 `maps_regeocode` 反查得到 |
| 起点 | 经纬度坐标，或地点名（地铁站/商场/酒店/路口） | 坐标可直接用；地点名需 `maps_geo` 解析 |
| 地点类型 | 咖啡 / 餐厅 / 公园 / 便利店 / 药店 … | 从用户措辞中抽取关键词 |
| 步行时间上限 | 如"步行不超过 15 分钟" | 未给定时不设硬上限，但优先推荐 15 分钟内 |
| 推荐数量上限 | 如"最多 3 家" | 未给定时默认 3；**任何情况都不超过 3** |
| 排序偏好 | 如"优先近一点" | 默认按步行时间升序 |
| 其他偏好 | 如"安静""人少""有户外座""适合带孩子" | 无数据支撑时只作为筛选提示，不写进理由 |

需求含糊时（例如"附近有什么好玩的"）**不要反问**，按"最通用的地点类型 + 15 分钟步行 + 3 个"直接给一版结果，并在结尾用一句话说明你的默认口径，方便用户下一轮修正。

### Step 2｜确定起点坐标

- 用户直接给坐标（`经度,纬度`）→ 原样使用，不做换算、不四舍五入。
- 用户给地点名 → 调 `maps_geo(address="<地点名>", city="<城市>")`，取返回的第一个 `location`。
  - 若返回多个同名结果，选与用户描述（城市、区、地铁线路）最匹配的一个，并在回答中写明"起点按 XX（地址）定位"。
  - 若返回为空 → 尝试用 `maps_text_search(keywords="<地点名>", city="<城市>", citylimit=true)` 取第一个 POI 的坐标；仍失败则如实告知起点无法定位，请用户补充更具体的地址或直接给坐标。
- **不要用 `maps_ip_location` 猜起点**：那是网络出口定位，和用户实际位置无关，用错会让整份推荐偏到另一个区。
- **起点坐标必须记录完整精度（6 位小数）**，后续所有路线调用都用这同一个坐标，保证"同一起点"口径一致。

### Step 3｜地点搜索（周边搜索为主）

**关键词映射**（用户说 → 传给 `keywords`）：

| 用户说 | keywords |
|---|---|
| 咖啡馆 / 咖啡店 / 喝咖啡 | `咖啡` |
| 餐厅 / 吃饭 / 好吃的 | `餐厅`（细分时用 `火锅`/`面馆`/`日料` 等） |
| 公园 / 散步 / 遛弯 | `公园` |
| 便利店 / 超市 | `便利店` / `超市` |
| 药店 / 医院 | `药店` / `医院` |
| 奶茶 / 甜品 | `奶茶` / `甜品` |

**首次检索半径**（按步行上限换算，含路网绕行余量；取整到 50 米）：

| 步行上限 | radius |
|---|---|
| 5 分钟 | 300 |
| 10 分钟 | 600 |
| 15 分钟 | 900 |
| 20 分钟 | 1200 |
| 30 分钟 | 1800 |

调用：`maps_around_search(keywords="咖啡", location="120.15,30.27", radius="900")`

- 坐标格式固定为 `经度,纬度`，**英文逗号，无空格**；不要传中文逗号、不要拆成两个字段。
- **结果不足时扩半径**：若有效候选数 < 目标数量，把 radius 放大到 1.6 倍再查一次；最多扩 2 次（即最多 3 次周边搜索）。扩半径是"找更多候选"，**不是放宽时间上限**——所有候选仍要过 Step 5 的路线校验。
- 周边搜索仍不足时，可用 `maps_text_search(keywords="<关键词>", city="<城市>", citylimit=true)` 兜底补候选，但同样必须过路线校验。
- 用户要求"公园""景点"等面积型地点时，注意 POI 的 `location` 是入口/中心点，路线终点用它即可，不要自行改写坐标。

### Step 4｜候选预筛（省调用、保质量）

1. 从 POI 列表中剔除：`typecode`/`type` 与需求明显不符的（例如找"咖啡"时混进来的"便利店""奶茶店""咖啡器具零售"）；名称明显是无关业态的。
2. 按 POI 返回的直线 `distance` 从小到大排序，**取前 6 个**作为待校验候选（最多 8 个）。理由：路线调用次数有限，且远端的点大概率超时。
3. 若对某候选的类型拿不准，可调 `maps_search_detail(id="<POI ID>")` 核对 `type`，确认后再进入路线校验。

### Step 5｜步行路线校验（数据真实性的关键一步）

对每个候选：

```
maps_direction_walking(origin="<起点经度,纬度>", destination="<该POI经度,纬度>")
```

- 从返回的 `paths[0]` 中取 `distance`（单位：米）与 `duration`（单位：秒）。
- 若 `paths` 为空或调用失败：该候选**直接剔除**，不要用直线距离顶替，也不要保留在推荐里；若失败数 ≥ 2，在回答末尾补一句"有 N 个候选的步行路线查询失败，已排除"。
- 不要传 `destination` 为地址文本，必须是坐标。
- 同一候选只需查一次，不要重复调用。

### Step 6｜过滤与排序

1. **硬过滤**：`duration/60` ≤ 用户步行上限（严格 ≤，向上取整后比较更稳妥，例如 900 秒 = 15 分钟可保留，960 秒 = 16 分钟必须剔除）。
2. **类型复核**：确认仍在候选里的地点确实属于用户要的类型。
3. **排序**：默认按步行时间升序（`duration` 升序，时间相同则按距离升序）。用户说"优先近一点"就是这条规则，且**列表顺序必须与之一致**，不能出现第 3 个比第 1 个更近。
4. **截断**：取前 `min(用户数量上限, 3)` 个。

### Step 7｜生成回答

用表格 + 简短说明。字段与顺序固定：

**推荐结果（从 XX 出发，步行 ≤ 15 分钟）**

| # | 地点 | 地址 | 步行距离 | 步行时间 | 推荐理由 |
|---|---|---|---|---|---|
| 1 | XX咖啡（XX店） | XX区XX路XX号 | 420 米 | 约 6 分钟 | 步行 6 分钟可达，是候选中最快的，沿 XX 路直行，路线简单 |
| 2 | … | … | … | … | … |
| 3 | … | … | … | … | … |

表格后补 1～3 句说明（按需）：
- 筛选口径：如"起点按 XX 站 C 口定位；步行距离与时间均为高德步行路线规划结果"。
- 数量不足时：如"15 分钟步行范围内只找到 2 家符合要求的咖啡馆，已全部列出"。
- 建议放宽：如"若可以放宽到 20 分钟，附近还有更多选择，需要我扩大范围再查一次吗？"

**推荐理由写法**：一句、不超过 25 字、**必须挂靠真实数据**（步行时长/距离/地址特征/路线特征），例如"步行 8 分钟，是本次候选里第二近的"。禁止写"环境很好""评分很高""很受欢迎""网红店"等无依据评价。

**单位规则**：距离 < 1000 米用"米"取整；≥ 1000 米用"公里"保留一位小数。时间用"约 N 分钟"（`duration/60` 四舍五入）。

## 4. 异常与边界处理

| 情形 | 处理方式 |
|---|---|
| 起点无法解析 | 说明"未能定位到起点"，请用户补充更具体地址或直接给坐标；不要猜一个坐标继续查 |
| 周边搜索返回 0 条 | 扩半径重试（≤ 2 次）；仍为空则说明"起点 X 米范围内未检索到 XX 类地点"，并建议放宽类型或距离 |
| 有 POI 但全部超时 | 明确说明"步行范围内（≤ N 分钟）没有符合条件的 XX"，**可**附 1 个"最接近但超时"的候选作为参考，但必须单独标注"步行约 X 分钟，已超出你要求的上限，不计入推荐" |
| 符合条件数量 < 用户要求 | 如实给出实际数量并说明原因，不用低质量或不相关的点凑数 |
| 步行路线调用失败 | 剔除该候选，不降级为直线距离；失败 ≥ 2 个时在文末说明 |
| 工具整体不可用/超时 | 明确说明"高德服务本次查询异常"，不输出任何未经查询的地点 |
| 用户追问"好不好吃/人多不多/现在还开吗" | 回答"这类信息高德接口未返回，未核实"，可建议用户查看高德 App 实时信息 |
| 用户给的是"我在地铁站"但没说是哪个站 | 按上文默认口径先给一版，并注明所用起点；不要停在提问上 |

---

## 5. 调用预算与效率

- 典型一次任务：1 次 `maps_geo` + 1～3 次周边/关键词搜索 + 最多 6 次步行路线 ≈ **不超过 10 次调用**。
- 不要对全部 POI 逐个查路线；先按直线距离预筛前 6 个。
- 不要为了"更全面"重复调用相同参数；同一坐标 + 同一目的地的路线只查一次。

## 6. 回答前自检清单

1. 每个推荐地点的名称与地址，是否都能在工具返回里逐字对上？
2. 每个推荐地点是否都有一次成功的 `maps_direction_walking` 结果？距离/时间是否直接取自该结果？
3. 有没有超时的地点被写进了推荐？数量是否 ≤ 用户上限且 ≤ 3？
4. 列表顺序是否与步行时间升序一致？
5. 推荐理由里有没有出现无法核实的形容词（环境、排队、评分、营业状态）？
6. 结果不足 / 查询失败时，是否已经如实说明并给了放宽建议？

## 7. 禁止事项

- ❌ 编造地点、地址、门牌号、坐标、POI ID
- ❌ 用直线距离或"半径 ÷ 步速"代替步行路线结果
- ❌ 把超时地点混入推荐清单
- ❌ 为凑满 3 个而推荐类型不符或位置不合理的点
- ❌ 输出"附近有很多不错的选择"这类无信息量的话
- ❌ 在回答里暴露 API Key、内部工具参数或调试信息
